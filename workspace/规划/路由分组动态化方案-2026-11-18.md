## 一、白话：要解决什么

你有一堆 AI 厂商（订阅账号和 API key），magpie 把它们排成队伍替你接活。要改的是三件事：

1. **① 动态能力**：分组（routing group）把几家厂商捆成一个名字供 agent 使用。除 Smart 外的十种排序（In order、In turn、Balanced…）由库内的 rotation 插件注册并默认开启（`plugins/rotation/rotation.go:26` `Essential: true`；有人用时即使插件被关也会被强制打开，`internal/pluginrt/config.go:159-166`），用户把插件关掉时这些排序按文档化设计回到"按列表序"（`rotation.go:8-11`、`app.js:12316-12318`）——**这个关掉的语义是设计，本方案不动它**。要补的动态能力是：新增一种"综合评分优先"的排序，让分组随厂商表现自己变，并且把它从常量、白名单、开关、界面**四件套一次接全**（缺任何一件都会复刻"设了不生效"）。
2. **② 评分优先**：给每个厂商模型算一个多方面综合分（成功率、首字速度、吞吐、配额余量、能力标签），分数高的排前面，分数与依据在路由轨迹里可见。
3. **③ 稳定兜底**：判定哪些厂商"特别稳"，在分组末尾加一个**组外的**稳定成员当兜底——组内常规候选全失败时由它接住，任务不至于烂尾；同时不让兜底被异常流量拖垮、不来回换人横跳。

**全部挂在现有机制上改，不推倒重来。** 现有可挂的 hooks：健康分（`internal/gateway/health.go`）、速度统计（`speed.go`）、配额分层（`routes.Seat` 的 Class/tier）、rest 冷却（`restAfterMarked`）、rest 后台探活（`rest_probe.go`）、affinity 替身回退（`affinity.go`）、厂商级 Fallback 链的铺设样板（`planFallbackGroup`）。

## 四、详细设计

### A. `score` 排序四件套（一次接全，缺一即"设了不生效"）

**A1 常量**：`internal/provider/routing.go` 常量区（:25-58）加 `Score = "score"`。

**A2 白名单**：`keptRouting`（routing.go:68-80）switch 加 `case Score: return true`——不加这条，`SaveGroup`（group.go:1513-1515）和 `Save`（provider.go:1715-1717）保存即清空。rotation 插件的 InUse 计数（`provider.Routings()`）随之把 score 视为使用中，强制开启语义（config.go:159-166）与其余十种一致。

**A3 策略本体**：新文件 `internal/routes/score.go`：

- `Strategy{ByUse: true, BySpeed: true, ByHealth: true, Order: scoreOrder}` 加入 `routes.Builtin`（strategies.go:520-531）→ rotation 插件以裸名 `score` 自动注册（rotation.go:26-31），无需任何注册代码。
- `routes.Seat` 加 `Health float64`；`Strategy` 加 `ByHealth bool`（routes.go:115-139，仿 `BySpeed` 模式：置位时 gateway 才读健康分，其他策略零成本）。
- `weighRouted`（routing.go:2431-2434 填 Seat 处）加：

```go
if st.ByHealth {
    wg.health = healthSeats(cs, now)   // 一次锁批量快照，见下
    for i, c := range cs { seats[i].Health = wg.health[c.restID()] }
}
```

- **`healthSeats`（health.go 新增）**：复用 `markOf`（health.go:264-292）一次锁批量快照返回 `map[string]float64`。**不新增每候选一锁**——热点③自检项（§六）。
- **`scoreOrder` 分层排序**（层优先于加权，防止"配额将尽的 99 分"排到"配额充裕的 85 分"前面烧穿）：
  1. **层 0 配额层**：沿用 `seatTier`（strategies.go:16-30，90%/98% 两线）与 `Loses`。
  2. **层 1 可靠层**：`Failures>0` 置后（多者最后）；`Resting` 置后（restLast 再兜一层）。
  3. **层 2 综合分**（权重常量写在 score.go 顶部，注释"改源码可调，GUI 不暴露"）：

| 维度 | 权重 | 分数来源 | 归一 |
|---|---|---|---|
| 成功率（健康分） | **0.40** | `Seat.Health` ← `healthPoint`（health.go:60-64）——已有字段 | 0–1 直用 |
| 首字速度 TTFT | **0.18** | `Seat.TTFT` ← `speedRec.ttft`（speed.go:31-40）——已有 | `1 - min(ttft/3000ms, 1)` |
| 吞吐 TPS | **0.12** | `Seat.TPS` ← `speedRec.tps`——已有 | `min(tps/60, 1)` |
| 配额余量 | **0.20** | `Seat.Used` 与 `Seat.Pace`——已有 | 两者各半 |
| 能力标签 | **0.10** | **`Provider.Caps map[string]ModelCaps`**（`internal/provider/provider.go:543`；`capability.go:301-306` Tools/Vision/Stream yes/no）——已有探测，**不新增探测** | 请求需要的标签全 yes=1；探测为 no 的所需标签=出局（层外剔除）；无要求=1 |
| （无数据兜底） | — | TTFT/TPS 无测量记中性 0.5；`Health` 无记录走先验 1.0 | 不罚不奖，新厂商有公平起点 |

  - 权重理由：成功率独大（本周痛点是断联不是慢：16915 次尝试中 698 条整链零 200）；速度合计 0.30 体现"效率更高"；配额 0.20 但层 0 已兜住烧穿；能力 0.10 仅软偏好（硬过滤另有 perKeyBarred/roomy）。速度合计低于成功率，"快而不稳"压不过"稳而稍慢"。
  - 同分回到列表序（prompt cache 温热，Balanced 同款尾规则，balance.go:58-59）。

### B2. 24h 计数器与健康分持久化（重启不丢）

新文件 `internal/gateway/score_store.go`，照 `rest_store.go` 模式（restsPath :29、saveRests :93 改名覆盖原子写）：

- 落盘：`{health: {restID: {wins, loss, run, at}}, counters: {restID: {attempts24h, fails24h, hardRests24h, lastReset}}, stableSince: {restID: 时刻}}`，上限 4096 条（health.go:225 清理线同款）。24h 滚动窗口靠 `lastReset` 到点重置（非逐条衰减，实现简单且口径可解释）。
- 写盘时机：**10 分钟节流定时器 + 进程退出 flush**（`FlushScores` 挂 `internal/cli/signals.go:47`、`internal/gui/handover.go:174` 现有 FlushSticks 旁）。**绝不挂进每请求路径**——热点①自检（§六）。计数器自增在既有锁内整数自增，无新锁。
- 读盘：`gateway.New()`（gateway.go:577）回读一次，健康分经 `decayed` 衰减到当前时间。
- `HealthPersist` 开关（默认开，关=内存态现状）。
- speed 不持久化（20min 半衰快变量，重启重测便宜）。【取舍】

### C1. "稳定厂商"判定（目标③的判定标准；口径改为 B2 计数器）

新文件 `internal/gateway/stability.go`，纯统计不改路由行为（灰度第 1 步先合）。**判定与 health.go 分工**：health 分是路由时的实时置后信号（30min 半衰，改动只有 C3 的 run 计数）；C1 是 24h 窗口的厂商级判定，只读 B2 计数器——这样兜底职责对健康分中性（C2）不会污染判定：

| 级别 | 判定（常量写死，GUI 只显示结果） | 数据来源 |
|---|---|---|
| 不稳 | 24h 失败率 > 20%（即成功率 < 0.80）或 24h 硬休息 ≥ 2 次 | B2 counters |
| 观察中 | 其余有记录者 | B2 counters |
| **稳定** | `attempts24h ≥ 8` 且 24h 成功率 ≥ 0.98 且 `hardRests24h = 0` 且不在探活失败名单（`restProbes.missed`，rest_probe.go:97-107） | B2 counters + rest_probe |
| **兜底资格** | 稳定保持 ≥ 24h（B2 存 stableSince） | B2 |

- **硬休息口径（对上版"每次 rest 都计数"错误的修正）**：挂钩在 `restAfterMarked`（routing.go:1365）返回处，条件为 `r.By != "off" && r.Until.Sub(now) >= time.Hour`——配额窗口/信用按天/受限与 key 拒绝 24h 计入；**1min 起步的限流 rest（≤30min）、`failProxy` 的零值 Until rest（:1440-1443 返回 `By:"cooldown"`）、内容过滤与 499（`By:"off"`/try.Gone）一律不计**。一次条件判断，无新锁。
- attempts/fails 的口径沿现状：499 与 agent 断联（try.Gone）不计失败；内容过滤（`failRefused`，`By:"off"`）不计；`noteUnstable` 现有计入点（gateway.go:3726/4215/4675、routing.go:1609）不动。
- 判定结果进 `ProviderHealth` 返回的 `Health`（health.go:148-153 加 `Stability string`），GUI 厂商行显示"稳/观察/不稳"徽标。
- 本周数据预演（输入"独立复核口径"，示意非承诺）：meoo(692/0)、ai(620/0)、opencode-zen-free(462/0)、coarena(260/0)、tokenrhythm(1512/1)、dumate(8233/3) 大概率进"稳定"；groq(194/197)、gemini(56/56)、zed(46/46)、codar(14/14)、qoder(9/9) 进"不稳"。

### C2. 组级兜底 Guardian（目标③落点；**只能组外成员**——结构性解决上版三处硬伤）

**组结构加一个字段**（group.go:168-288 内）：

```go
// Guardian 是兜底成员：组内常规候选对一次请求全失败后，最后加试的
// 组外成员——"provider/model"或"group/<id>"；"auto" 由 magpie 每次挑
// 同名模型的组外最稳厂商。空为无兜底。
Guardian string `json:"guardian,omitempty"`
```

**为什么只能是组外成员（对评审③重/④重的正面回应）**：
1. **probeOne 冲突**（fallback.go:1169-1205、gateway.go:2846）：组内成员在全常规失败场景下恰是刚失败 resting 的键，再铺一次要么被 probeOne 剔除（兜底跳空）、要么对着刚失败的键原地重试（#1799 明言要消灭的 doomed try）。组外成员未参与组内失败，铺上时是清醒的，**append-only-when-awake**（resting 的组外兜底本次请求不铺）——probeOne 永远见不到 resting 的 Guardian，两个坑都不存在。
2. **affinity 不变式**（affinity.go:704-710）："A routing group's members are never fallbacks"——组外兜底使这条明文假设**继续成立**，`backToMain`（:710）、`standsIn`（:870）、`standsInFor`（:751-776）、`leastHeld`（:796）、`backFromStandIn`（:737）的走向经本会话逐一核过：Guardian 打 `Fallback=true`、`place=len(ms)+1` 排末位后——不被新会话粘住（leastHeld/readyForNew 跳过）、主位恢复即回（backToMain 的 `!order[0].Fallback` 对组外兜底恒真）、answeredStanding 语义正确（standsInFor 对 place 末位者返回 true）。改动：**更新 :704-708 注释**补一句"组的 Guardian（组外成员）是打 Fallback 标的另一方"，并按 `affinity_fallback_paths_test.go` 样式补回归用例（affine 各 mode 下 Guardian 不被提前、不成为会话归属）。
3. **拖垮与换人乒乓**：兜底不是组内最稳成员本人，其常规排位不被兜底职责直接影响；剩余风险与防线见下。

**auto 的定义**：同名模型的组外最稳厂商——复用 autoGroups 的同型归并口径（`catalog.SameModel`，group.go:829 与 :772-825 的 mergeKey 逻辑）：每次 planGroup 时，找服务同一模型、不属于本组成员、非本组 Classifier、C1 判定 ≥ 稳定且清醒的厂商，取稳定级最高者（同级取目录序首个）；无符合条件的**不铺兜底**（宁缺毋滥，不猜）。组内没别人服务同名模型时 auto 即为空，GUI 如实显示"暂无组外同名模型可兜底"。

**铺设点**：`planGroup`（fallback.go:600-615）末尾，仿 `planFallbackGroup`（:562-586）：先解析 Guardian 并与本次 `ms` 的成员名单核对（含 Match 本次匹配者，`placed` 所用的 `m.Path[0]` 同源）——**落进组内则本次跳过兜底**。保存时的组外校验挡不住 Match 模式日后扩展把某个厂商卷进组里（组员名单每次读组现算），铺设时重查是第二道闸。核对通过后对该成员走 `perKeyBarred` 取键 → `weighed()` 组装 → `Weighed.Fallback=true`、`Via=[g.ID]`、`place=len(ms)+1`、候选加 `guardian bool` 字段 → append 到 out 与 pl.order 末尾（保持 `demoteUnstable` 要求的 len 对齐，health.go:332）。之后白拿：try loop 自动排最后一跳；失败照常走 rest 阶梯 + `probeOne` 剔除语义 + all_down 告警（guardian 也 resting 时的行为与今天完全一致）。

**兜底职责对健康分中性（对评审④重的核心防线）**：候选加 `guardian` 字段后，六处记分点跳过 guardian 候选——`noteStable`（routing.go:95，servedCandidate 内的其余清理照旧：清 rest、probeAnswered 等）与 `noteUnstable`（routing.go:1609、gateway.go:3726/4215/4675、continuation.go:786）各加 `if !c.guardian`。理由：兜底接的是"别人全失败"的毒请求，它的失败率不代表它的常规可靠性（先例：forbiddenAlike routing.go:140-149 判"两次同型拒绝是请求的错"；#1799 判 doomed try 不该烧候选）。**保持计数的**：rest 阶梯照常（失败照样休息，1min 指数递增封顶 30min，风暴中被自然熔断）；`routed.failures` 照常计数（seat 级、答一次即清、寿命远短于健康分——残留影响：风暴中该厂商在 Balanced 的 vendor-failing 维度暂时置后，属正确反应，答一次即恢复）；B2 计数器中 guardian hop 的 attempts 计入、fails **不计入**（口径与"毒请求不是它的错"一致）——因此风暴不会把兜底厂商投成"不稳"，不会触发 auto 换人。

**auto 换人防乒乓（评审④重的第二道防线）**：auto 选择结果粘滞——每 15 分钟重评一次，仅在当前兜底厂商掉到"不稳"或发生硬休息时才换人，否则保持（B2 存当前选择）。不存在按请求粒度换兜底。

**SaveGroup 校验**（group.go:1411，加在 :1513 keptRouting 检查附近）：
- Guardian ∈ {"", "auto"} 或合法成员引用（`provider/model` / `group/<id>`）；
- **不得是本组成员**（含 Match 当前匹配者，matchesIn 现成）——组外性由保存时强制；
- 不得是本组 Classifier（分类器已在每请求前置调用，兜底再指它会造成故障放大）；
- Guardian 指向组时不得指回本组或包含本组的组（沿用 SaveGroup 现有的环拒绝，深度 ≤8 与 Members 同规）；
- Guardian 不参与 Weights 计数、不受 Rules/Classifier 指派、不进 Levels/Fast。

**默认值（对评审⑤中的修订）**：**新组 Guardian 默认空（关）**，撤除上版"新组默认 auto"的行为面变更；组卡一键"自动兜底"（写入 auto）与"选成员"并列，auto 只在 `AutoGuardian` 开关开启时生效（见 D）。目标③由"一键 + 徽标指引"达成，是否进一步默认开由灰度第 4 步数据决定后再议（阶段知会）。

### C3. 防乒乓滞回（仅相对线分支；修正上版的数学错误）

- `healthPoint`（health.go:60-64）加 `run int`（当前连续成功次数）；`noteID`（:211-233）`ok` 时 `run++`、`!ok` 清零——锁内整数读写，零新锁。
- `demoted`（:301-323）**只在相对线分支**加滞回：`s < m.best*healthShare` 时，若 `h.run < healthRebound`（新常量 =3）则保持 demoted。**绝对线分支（`s < healthDemote`）不加 run 判断、行为不变**——因为 `scoreOf=(wins+1)/(wins+loss+1)`（:295-297）在 loss 大时三胜根本过不了 0.5（衰减后 W=0、L=8 加三胜 = 4/12≈0.33），上版"3 连成功后分数必然过线（两分支自洽）"是数学错误，本版撤回。绝对线置后者的恢复与今天一样由 30min 半衰自然衰减驱动；滞回的收益是堵住相对线上的"一胜即回前排→再败又置后"循环（本周首跳失败 1294 条里反复首跳的那批）。
- 无记录者不受影响（`wins+loss < healthEnough` 已提前返回 false，health.go:319-321）；`resetHealth`（:238-242）语义不变。
- `StabilityGuard` 开关（默认开）关掉时 demoted 完全回现状。

## 七、风险与"不做"清单

**风险与对策**

1. score 改变选择顺序 → 灰度第 3 步、`ScoreRouting` 一键关、决策日志前后对照；auto 组默认不动（撤上版假设）。
2. 小样本误判稳定/不稳 → `attempts24h ≥ 8` 门槛，不足一律"观察中"。
3. Guardian 级联/环/自指 → SaveGroup 五条校验（§C2）。
4. 兜底厂商在风暴中被拖垮的**残留风险**（如实声明，非零）：guardian hop 对健康分中性、B2 fails 不计、rest 阶梯熔断、auto 15min 粘滞四道防线后，仍剩 `routed.failures` 短期置后（正确反应）与硬休息导致换兜底（正确反应）；极端全量风暴下兜底也会 rest，行为退化为今天的 all_down 告警——**不会比现状差**。
5. 内容过滤、499、代理故障误伤评分 → C1 硬休息口径（≥1h 或长休类型）+ attempts/fails 口径沿现状（499/`By:"off"`/try.Gone 不计）；`failProxy` 的 `By:"cooldown"`+零值 Until 被 `Until.Sub(now) ≥ 1h` 条件天然排除（§C1）。
6. C3 滞回对绝对线置后者无效（数学所限）→ 如实接受：绝对线恢复仍靠半衰，灰度第 2 步的预期按此设定，不以滞回为其背书。

**不做（明确排除，防范围蔓延）**

- **不动 rotation 被关时的"回到列表序、下拉只剩 Smart"语义**（rotation.go:8-11、app.js:12316-12318，文档化设计）；不提供"关插件后核心继续服务"的路径。
- 不改 `routes.Find` 对其余十种排序的任何行为（上版 A1 撤除）。
- 不动 saveRoute/prune 与决策日志写盘架构（热点①②根治另立方案，本方案只保证不加重）。
- 不扩能力探测维度（Tools/Vision/Stream 之外不发任何付费探测请求）。
- 不做跨进程/分布式评分共享。
- 不改 Balanced/Smart 的现有维度序（可配诉求由 score 承担）。
- 不自动修改用户自建分组的路由与成员顺序；新组 Guardian 默认空。
- Guardian 不做组内成员（probeOne 与 affinity 不变式的结构性约束，§2.5）。
- 不引入数据库/外部依赖。
- 不做通用 Chat 上游"干净截断"检测（属协议判定问题，与本方案无关）。
